# 0007 - 统一供给池：账号音源与三方音源池化融合

日期：2026-10-15 ｜ 状态：已实施（同日重写落地，见文末实施记录）

## 背景

0005 建立账号↔三方双通道平级分发，0006 把三方推广为音源池并完成（成员 × 平台）熔断。分发器此时已是半个连接池调度器：名册、（平台 × 音质）能力过滤、健康过滤、在途最少者优先、失败转移、恢复等待——但账号与池仍各持一套健康状态、两段式尝试预算（池 ≤2 + 账号 1）与硬编码音质门槛，且「一平台 N 账号」的未来会要求凭据层与调度层同步改造。维护者提出按数据库连接池思想融合：池按（平台 × 音质）记录可用供给源，任务到来取空闲者，未来加账号只是名册追加。

经设计评审（grilling 全树走查），确认类比成立但有四处异质必须显式建模：信任面与失败含义（账号失败 ≠ 账号死亡）、健康语义（冷却 = 平台强加 vs 熔断 = 自我计数）、节流（账号平台间隔 vs 脚本 2s）、音质能力（官方直链契约 vs 脚本声明不可信）。

## 决策

**账号音源与三方音源池融合为统一供给池：成员统称供给源，分发器泛化为单循环调度。**

1. **供给源（Provider）**：统一池成员，把一首歌解析成下载链接的一个实例。两类：账号供给源（用户平台会员凭据的解析实例）与脚本供给源（用户导入的音源脚本沙箱实例；2026-10-20 起无内置，见 0006 备选翻案）。每供给源声明（平台 × 音质）能力与自身节流。
2. **调度纯看空闲**：分发器单循环——能力过滤 → 健康过滤 → 在途最少者优先，不看条目身份。0005 第 2 条「同时可用优先账号」tie-break 翻案废除（2026-10-15 维护者决定，接受官方直链比例下降与三方流量占比上升）。
3. **健康模型双通道**：每供给源一个 `brokenUntil`、两个写入入口，概念保持分离——**冷却**（账号风控：平台强加、立即生效的外部信号）与**熔断**（脚本连败自计数：3 败 → 1 分钟，翻倍 1→2→4→8 封顶 8 分钟，同平台下载成功归零（解析成功不清零，见 0006 决策 5 OCR 收紧），解析与下载回灌记账——0006 决策 5 平移）。
4. **账号不记连败**：版权缺失、vip 限制、偶发网络错是账号的正常失败，任务自动转移下一个供给源；账号供给源只认冷却，避免 vip 曲库连续失败冤杀健康账号。
5. **音质政策门槛**：脚本供给源声明再高只接 128k；flac/320k 仅账号供给源（0005 第 4 条延续，不信脚本自我声明；未来可按源解禁）。
6. **风控转移泛化**：任一供给源风控/熔断，本任务跳过它继续下一个供给源；全部不可用回等待，恢复点按平台过滤（0006 池侧机制泛化到全池）。
7. **范围只融合解析分发层**：兜底链（生效音源）与下载失败换源留在池外当最后手段——换源改的是「歌」不是「源」，语义上不是解析通道；兜底链与池内同脚本成员的去重判断保留。播放链路不变（0005 第 6 条延续）。
8. **实施方式**：分发器 + 账号通道 + 池一次重写为纯池模型（维护者选定，接受回归风险）。重写必须保留 issues source-pool/01,02 与 stall-retry 的全部已修行为：下载回灌记账、换链前记账与重归因、风控错误不进兜底链/换源、恢复等待唤醒、写盘/路径类本地故障不记账。

## 备选

- **统一抽象·增量迁移**（先定供给源接口 → 两类条目套接口 → 分发器单循环，每步可验证可停）：更稳但周期长 → 维护者选择一次重写，本条留档为回退蓝本。
- **只写文档不动代码，等 N 账号需求落地再融合** → 维护者要求现在定模型（本文档即产出），代码按决策 8 执行。
- **全条目统一连败熔断**（含账号）→ 模型最简但 vip 曲库连续失败会冤杀健康账号 → 拒绝。
- **声明驱动音质能力**（脚本声明 flac 即接 flac 活）→ 三方码率不保证与官方一致，高音质官方直链契约维持 → 拒绝，保留政策门槛。
- **兜底链入池参与统一调度** → 与池内同脚本成员去重复杂化、最后手段建熔断状态无收益 → 拒绝。
- **保留「同时可用优先账号」** → 与纯空闲调度二选一，维护者选后者 → 0005 决策 2 部分（tie-break）翻案废除，平级分发的其余结论不变。

## 后果

- 混跑时官方直链比例下降，脚本供给源流量占比在 0005 的 ~70% 基线上进一步上升；账号请求量随之下降，风控窗口更少的良性循环增强。
- 「N 账号 0 改动」只对分发器成立：凭据层（每账号凭据槽、独立队列/间隔/冷却、凭证状态 UI）是未来独立工作，本 ADR 不覆盖。
- 回归风险集中在一次重写：需对决策 8 列出的已修行为逐条回归验证（真机 + `[pool]` 日志），无自动化测试基建。
- 词汇表同步改写：新增「供给源」「供给池」，「池成员」并入，「通道分发」「熔断」「兜底链」词条按本决策更新。

## 实施记录（2026-10-15）

- `renderer/store/download/providerPool.ts`：统一供给源选择层——名册（账号 `account:<platform>` + 脚本 userApi id）、纯空闲选择（平局按名册序落在脚本供给源）、按（平台×音质）的恢复点查询、账号在途记账（按平台，跨并发共享）。
- `renderer/store/download/spillChannel.ts`：收窄为脚本供给源后端（节流/熔断/能力上报/沙箱解析），名册与能力查询导出给选择层；`poolPickMember` 被 `pickProvider` 取代移除。
- 分发器单循环：转移预算 3（等价旧 账号1+池2）；「全部供给源恢复期」提前回等待（不进兜底链），语义等价旧双通道提前等待。
- **调度范围变化**：kw/mg 与未登录平台的 128k 任务原走单链出口（生效音源），现纳入供给池调度（实施时有内置野花全平台兜底「128k 恒有可分发供给源」；2026-10-20 内置拆除后，空池时 128k 回落单链出口，见 0006 备选翻案）；单链出口收窄为「无可分发供给源」（典型：非账号平台的 flac/320k，及空池下的 128k）。
- 等待/恢复判定从「平台」细化为「平台×音质」（flac 任务不再被脚本熔断窗口拖着空等）。
- 账号内联兜底保留：`buildAccountApi` 账号失败静默落生效音源（0005 延续），归因仍记 `sourceChannel='account'`；显式兜底链与换源留在循环外，风控门禁不变。
- 开放 API `/download-status` 新增 `sourceChannel` 字段（account/yehua/成员名），调用方可对账实际出链供给源。

## OCR 审查修正（2026-10-15，commit 7ee9eccb 复审）

- **换链缓存穿透补全**：池循环已穿透 `isRefresh`，但单链出口与「下载失败换源」两个池外出口仍硬编码 `isRefresh: false`，换链时会命中 URL 缓存原样返回死链 → 两处改为传递 `isRefresh`。
- **恢复期换链不再置错**：`handleRefreshUrl` 此前忽略 `wait`，全供给源恢复期换链会直接杀任务；现提取 `backToChannelWait`（与初始分发共用），退回等待队列、清掉死链，恢复点唤醒重解析。
- **熔断归零语义收紧**：解析成功不再清零计数，只有下载层成功（回灌 true）归零——防死链型成员在换链循环中败绩 0↔1 震荡、永不到阈值（0006 决策 5 同步修订）。
- **`sourceChannel` 持久化**：download_list 表加 `sourceChannel` 列（DB_VERSION 5→6 迁移），/download-status 对账数据重启后不再失真；注释明确 null = 未经供给池出链（含单链出口、兜底链与换源成功）。
- 误报剔除：`logToMain` 导入存在（ipc.ts:230）、`poolMemberId` 类型已声明（download_list.d.ts:79）、主进程仅注册野花/野草两个内置源（长青/幻音/全豆要不在线程内）。
