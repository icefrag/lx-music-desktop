# 01 - 应用退出后开放 API 服务不停止，端口持续占用

Status: resolved
Category: bug
Reporter: 用户（2026-10-15，dev 环境测试音源池期间发现）

## 现象

洛雪退出后，开放 API 的本地 HTTP 服务不退出，端口（23330）一直被占用。

## 已确认的代码事实（分诊时核查）

1. **退出链路无人停服**：`openApi` 的 `stopServer`（`src/main/modules/openApi/index.ts:459`）只有两个调用方——设置页开关（`rendererEvent/openAPI.ts:57`）和 `startServer` 重启前清理（`:478`）。整条退出链（托盘退出 `tray.ts:312 → quitApp()` → `app.quit()` → `before-quit`（`app.ts:216`，仅设置 `isSkipTrayQuit` 标志）→ `window-all-closed` → quit）**没有任何一处调用 openApi 清理**。HTTP server 与 SSE 长连接全靠进程死亡由 OS 回收；若 quit 被延迟（dev 模式常见），端口就一直占着。
2. **现行证据**：分诊时 electron 主进程（PID 4804）仍 LISTENING 127.0.0.1:23330。
3. **与音源池改动（ADR 0006）无关**：openApi 模块本轮未动；`main_window_close` 新增的 `closePoolChannels` 为 fire-and-forget 清理，不阻塞 quit，也不涉及 openApi。
4. **疑似设计行为的干扰项**：点窗口 X 时若 `tray.enable`（托盘常驻）→ `preventDefault() + hide()`（`winMain/main.ts:15-25`）——应用隐藏到托盘，进程与 API 活着是**设计行为**，不是本 bug。托盘退出才是真退出路径。

## 待确认（@用户）

2. 若是托盘退出后仍占用：退出后 electron 进程是否残留（任务管理器可见）？

## 修复方向（确认后可直接做，改动极小）

`before-quit` 钩子里补 `void stopServer()`（fire-and-forget，不阻塞退出）：进程真退时服务显式关闭；顺带消除 dev 模式下 quit 被拖慢时端口滞留的窗口。

### 2026-10-15 分诊补充：根因修正 + 修复 + 复验

**用户答复**：没有托盘功能，都是直接退出（`tray.enable` 关闭）。

**根因修正（比初诊更深一层）**：端口滞留的直接原因不是（只是）「没停 openApi」，而是**退出链根本没走到 quit**：点 X → 主窗口关闭 → 各 `main_window_close` 监听器异步关隐藏窗口（userApi 沙箱 `closeWindow`/池 `closeChannel` 先 `await` 会话 `clearAuthCache/clearStorageData/clearCache` 再 `destroy()`）→ 任一清理挂起 → 窗口残留 → `window-all-closed` 不触发 → `app.quit()` 永远不被调用 → 进程 + 23330 存活。分诊当时用 WM_CLOSE 关掉残留窗口后进程立刻全退、端口释放，验证了这条链。

**修复（三处，均已实施）**：

1. **根因** `userApi/main.ts closeWindow` + `userApi/spillChannel.ts closeChannel`：先 `destroy()` 窗口，会话缓存清理改为后台 fire-and-forget——销毁不再被可能挂起的清理拖住
2. **兜底** `winMain/main.ts` close 处理：无托盘路径在 `main_window_close` 后显式 `app.quit()`（Windows/Linux）——退出不再依赖「所有窗口都乖乖关完」；托盘隐藏路径不变
3. **原报告诉求** `app.ts` `before-quit`：补 `void stopServer()`——开放 API 显式停机，端口释放不依赖进程死亡

**复验（dev 环境实测）**：向带修复实例的主窗口发 WM_CLOSE → 12 秒内 electron 进程树归零、23330 释放、dev runner 退出码 0。改动文件 eslint 干净，`build:main` 编译通过。
