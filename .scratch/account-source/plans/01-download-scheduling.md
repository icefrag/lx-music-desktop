# 方案 01 - 账号音源下载调度：避风控 + 保速度

Status: implemented (2026-10-14，渲染层/主进程编译通过；主进程仅剩 tx.ts/kg.ts 在途改动的 7 个既有类型错误，与本方案无关。真机验收未跑，见「验收标准」)

## 背景与现状

调度规则三条叠加（事实，见代码）：

1. 全局并发 `download.maxDownloadNum`，默认 3（`src/common/defaultSetting.ts:116`）
2. 单平台**整个任务级**串行：账号激活的 kg/tx/wy 同时只允许 1 个任务 RUN，取链 + CDN 下载全程独占（`src/renderer/store/download/action.ts:351` canStartBySourceLimit）
3. 主进程解析节流：同平台串行 + 最小间隔（默认 kg 8s / tx 3s / wy 3s，±20% 抖动）+ 风控指数冷却 10min→1h（`src/main/modules/accountSource/queue.ts`）

失败链：账号解析失败 → 静默回落当前音源（`src/renderer/utils/musicSdk/api-source.js:40`）；冷却期主进程快速失败（`src/main/modules/accountSource/index.ts:72`）。

## 问题诊断

| # | 问题 | 证据 |
|---|------|------|
| P1 | **保护过度**：任务级串行把风控保护扩大到 CDN 下载阶段。直链下载不带账号凭证、不碰平台 API（issue 02 已证实 tx 风控是接口层频率风控）。代价：同平台吞吐 ≈ 1/单首下载时长，10 首同平台 ≈ 10 × 单首时长 | action.ts:351 |
| P2 | **保护不足**：冷却期间排队任务被逐个立即调度 → 快速失败 → 静默回落免费源（会员音质丢失）或 ERROR。一批任务几分钟内烧光，冷却结束不自动恢复 | index.ts:72 + api-source.js:40 |
| P3 | **风控信号跨不过 IPC**：`RiskControlError` 实例不跨进程，渲染层只拿到 message 文本（无稳定前缀，对比 `account_expired: ` 模式），调度器无法区分风控与普通失败，做不了挂起策略 | index.ts:86 仅有 expired 前缀 |
| P4 | **interval 设置失效**：任务级串行下同平台同时只有 1 个解析在飞，两次解析隔着分钟级下载，秒级间隔形同虚设 | queue.ts:33 |
| P5 | 次要：启动校验探针不走队列且三平台并行（`Promise.all`）；wy 无风控错误映射（code 未识别，触发风控不进冷却） | index.ts:99 / resolvers/wy.ts |

## 目标设计

**原则：风控管「解析请求节奏」，速度管「下载并发」。两者解耦。**

### A. 解析级串行，放开发下载并发（吞吐核心）

- `canStartBySourceLimit` 从「同平台 1 个任务 RUN」改造为「同平台冷却中则跳过」（保留 `startDownloadTasks:438` 处的复用点）。
- 同平台多任务可同时 RUN，文件下载并行；全局仍受 `maxDownloadNum` 限制。
- 解析节奏完全交给主进程队列（已有串行 + 间隔 + 抖动 + 指数冷却），P4 随之解决——interval 设置真正生效。

### B. 冷却挂起 + 自动恢复（避风控韧性核心）

- **主进程**：风控错误跨 IPC 加稳定前缀（仿 `account_expired: `，如 `risk_control: `）；`Status` 增加 `cooldownUntil` 字段，风控触发/冷却设置时走现有 `setStatusBroadcast` 广播。
- **渲染层**：
  - 账号解析请求加 flag（下载链路声明「风控错误不回落」），播放链路保持现状即时回落——用户在等播放，不等冷却。
  - 调度器 `getStartTask`：平台冷却中 → 该平台 WAITING 任务不调度、不回落、不报错，保持 WAITING。
  - 渲染层按 `cooldownUntil` 自设 setTimeout 触发 `checkStartTask`，冷却结束自动恢复账号解析（主进程无需冷却结束定时器）。
- 效果：风控一次只损失「冷却时长」，不再损失整批任务。

### C. 默认值与探针（节奏调优）

- tx 默认间隔 3s → **5s**（issue 02：tx 频率风控激进且时间窗口波动；B 的挂起兜底就位后可观察再放宽）。kg 8s、wy 3s 不动。
- wy 补风控错误映射（接口返回异常 code 归类 RiskControlError），否则 B 对 wy 不生效。
- 启动校验探针纳入队列节流（或冷却中跳过），不再三平台并行直发。
- `requestInterval` 的 0（不限速）选项在 A 落地后等于裸奔（同平台任务会背靠背连发解析请求），给间隔加下限（如 1s）或移除 0 选项。

### D. 观测

- 冷却期间排队任务状态文本显示「风控冷却中，剩余 X 分钟」，而非误导性错误。

## 吞吐对比（估算，单首下载 40s、tx 间隔 5s）

| 场景 | 现状 | 方案后 | 提升 |
|------|------|--------|------|
| 10 任务 = 3 kg + 7 免费 | kg 部分 ≈ 3×40s = 2min | ≈ 40s + 2×5s ≈ 50s | ~2.4× |
| 10 任务全 kg（maxN=3） | ≈ 10×40s ≈ 6.7min | ≈ 4 批×40s + 取链 ≈ 2.8min | ~2.4× |

全局并发仍是最终上限；用户可在 A 落地后自行调大 `maxDownloadNum`（纯设置项）。

## 风险与对策

- **tx 风控窗口波动**：解析级限速不能根绝 500003——靠 B 挂起兜底，冷却后自动恢复，单次代价 = 冷却时长。
- **同平台多 CDN 并行下载**：直链不带凭证，低风险；解析成功后立即下载（现有流程不变），token 时效内完成。
- **解析请求变密集**：放开后 10 首同平台 = 间隔节奏下连续 10 次解析请求（此前隔着分钟级下载）。这是速度的代价面，由间隔值 + 冷却兜底控制，C 的默认值偏保守起步。

## 实施顺序（总计 ~4.5h）

1. B 主进程：risk_control 前缀 + cooldownUntil 广播（~1h）→ 验证：冷却中主进程广播 cooldownUntil
2. B 渲染层：挂起调度 + 冷却结束自动恢复 + 播放/下载回落分流（~2h）→ 验证：人为触发风控，排队任务保持 WAITING，冷却结束自动续跑
3. A：canStartBySourceLimit → canStartByCooldown（~30min）→ 验证：3 个同平台任务同时 RUN
4. C：tx 默认 5s + wy 风控映射 + 探针入队（~1h）→ 验证：日志时间戳间隔 ≥ 设置值
5. D：冷却状态文本（~30min）

## 验收标准

1. 3 个同平台账号源任务同时 RUN 并行下载
2. 同平台解析请求间隔 ≥ 设置值（日志时间戳）
3. 风控触发 → 排队任务保持 WAITING 不回落不报错；冷却结束自动恢复账号解析
4. 播放场景冷却中仍即时回落免费源，不等待
