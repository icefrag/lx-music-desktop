## 反馈原话

正在下载中有两个任务，已经卡住很久了，进度是不动的，但是没有触发 10 秒的重试。按之前的约定应该要自己暂停再启动，或者换音源的。

## 核实结论（代码审计）

10 秒看门狗本身闭环：`__startTimeout` 在 init/response/每个 data chunk 时重挂，
10s 无数据 → `download timeout` → stall 阶梯；HTTP 层另有 60s 请求超时兜底。
运行态能永久冻结的洞在 **`__handleComplete` 的干净截断分支**（Downloader.ts:244-247）：

- 服务器优雅关闭连接（`response.complete === true`）但字节数 < Content-Length
  → `status = stopped` + `emit('stop')`
- worker 的 `onStop` 只 `console.log`，不发任何 action → 无重试、无换链
- 且 `status = stopped` 使后续一切 `__handleError` 直接 return（`__handleError`
  对 stopped/completed 静默），看门狗已被 `__clearTimeout` 清掉 → **任务永久卡在
  RUN、进度冻结、无任何自愈**

b8b8cea9 修了孪生路径 `!response.complete`（→ 'download terminated'），
complete-but-short 这条漏了。

## 修复方案

1. worker `onStop` 改为 `sendAction(refreshUrl)`：孤儿 stop（干净截断）→ 换链恢复。
   用户主动暂停/删除路径不受影响——`pauseTask`/`removeTask` 都先删 `taskActions`
   再 `dl.stop()`，此时 sendAction 已是 no-op。
2. `STALL_ERROR_MESSAGES` 补 `'Request timeout'`（60s HTTP 兜底超时的报错文案），
   让连接阶段挂死也走 stall 阶梯（同 URL 重连 → 换链）而非同 URL 盲试到死。

## 边界确认

- 卡住的存量 2 个任务需手动暂停再启动一次（修复只防复发）。
- 根因属推断（渲染层日志不进 dev stdout，无法直接看到两任务的 stop 事件）；
  修复使该类卡死整体自愈，验收时观察是否还会出现无重试的冻结任务。
