# 05 - 128k 任务实际下到 FLAC 无损（部分供给源谎报音质）

日期：2026-10-15 ｜ 类别：bug ｜ 状态：已修复（双闸：解析层体积哨兵 + 下载层总大小守卫）；后缀矫正（方案 B）列为可选后续

## 现象

用户报告：下载的 128k 歌曲有的达到 40MB+。歌曲库 `D:\music-lib` 实测超过 10MB 的 `.mp3` 文件大量存在，最大 115MB（起风了）。

## 验证（已确认，非猜测）

对 5 个超大 `.mp3` 文件做魔数嗅探，全部同模式：

- 文件头是真 ID3v2 标签（内嵌封面图，大小 22KB~620KB 不等）
- ID3 之后紧跟 `fLaC` 魔数，其余全部是 FLAC 音频流
- 即：**128k 任务拿到的是完整 FLAC 无损**，被下载器按任务元数据 `ext: mp3` 写成 `.mp3` 后缀

样例：起风了 115.6MB（fLaC@250013）、若生命等候 92.7MB（fLaC@272678）、喜帖街 72.7MB、葡萄成熟时 53.9MB、披星戴月的想你 63.3MB。

对照：聆澜 API 实测 128k 诚实（tx/kg 均 4.3MB audio/mpeg）；嫌疑源为野花/野草后端（97.64.37.235）或其他导入成员——**具体是谁谎报尚未归因**（这批下载早于 dispatch 日志落盘功能，重启 dev 后复测一测便知）。

## 影响

- 128k 任务流量放大 10~30 倍（批量下载场景成本显著）
- 文件后缀 `.mp3` 与实际 FLAC 内容不符——部分播放器（老车机等）按后缀解析会播放失败
- 「128k」标签失真，用户对账困惑（本工单来源）

## 修复方向（待裁定）

- **A. 体积哨兵**：128k 任务按 `interval` 时长估算期望体积（约 时长×128kbps×1.1），实际下载体积超阈值（如 >2.5×）→ 视为源谎报，走换链转移重取（预算外则接受并标注）。根治流量浪费，代价是换链重下一次。
- **B. 后缀矫正**：落盘完成后嗅探魔数，FLAC 内容改写 `.flac` 后缀。最小改动，解决后缀说谎，但不省流量。
- **C. 接受现状**：无损当福利，仅文档记录（ADR 0005「128k 码率不保证与官方一致」的极端形态）。
- 组合建议：A + B。

## 备注

ADR 0005 后果区「128k 码率不保证与官方一致，用户已知悉并接受」覆盖的是码率偏差，本案是**格式级谎报**（128k 请求给无损），超出该边界原文语义，故按新 bug triage 而非既定边界回执。

## 实施（2026-10-15，方案 A）

`providerPool.ts` 体积哨兵：脚本供给源解析出 128k 直链后、下载开始前，Range 探针（`bytes=0-0`，8s 超时）取 `Content-Range` 总长，与按时长（`interval`）估算的期望体积（128kbps ≈ 16KB/s）比较，超 2 倍 → 按失败回灌该成员（计入升级熔断，惯犯自我隔离）并抛错，分发器转移下一个供给源。探针拿不到总长（无 Range/无 Content-Length/超时）不惩罚、放行下载——尽力而为的提前识别。账号线索单独落日志：`[pool] 成员 平台 体积哨兵：128k 期望约 X，实际 Y → 拒绝`。

## 实施（2026-10-15，第二道闸——根治）

哨兵只覆盖池内脚本供给源主路径；账号内联兜底出的生效音源链接、池外兜底链/换源链接绕过它。补下载层总大小守卫封死全部旁路：

- `common/utils/download/Downloader.ts`：新增 `maxTotalSize` 选项，`__initDownload` 响应头阶段（一字节未写）超限即中止并报 `download oversize`。
- `renderer/worker/download/download.ts`：128k 任务按时长估算期望体积 ×2 传入 `maxTotalSize`；`download oversize` 错误映射为直接换链（同 URL 重试无意义），`tryNum` 计次 >2 置错防死循环。

两道闸叠加后的覆盖：池内主路径在解析层拦截（省流量 + 熔断归因）；账号/兜底/换源及探针盲区在下载头阶段拦截（不落盘、换链转移，计次封顶）。残余边界：响应无 Content-Length 的源本来就会在 `__initDownload` 报 `Content length is 0` 失败（既有行为），不存在「无总长还能下载」的通道。
