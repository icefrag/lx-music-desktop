# 04 - QQ 音乐批量任务全部走账号，聆澜未参与

> *This was generated by AI during triage.*

**类别**: bug（待定）｜ **反馈人**: wuirui ｜ **日期**: 2026-10-15

## 反馈原话

跑了一个 QQ 音乐的任务，全部走的都是账号音源，没有走新加的音源聆澜。

## 已查明的事实

1. 批次运行的 dev 实例不是我能读日志的那个（该实例整份日志仅 1 次 tx 账号解析
   `vkey(M500004eLfht3q9gQc)`，与 11 首批次不匹配）——用户自行重启过 dev，日志不可见。
2. 聆澜脚本不含 'Fail' 字面量；日志里仅有的 4 次池解析失败仍是野花上游（同 issues/02）。
3. 分发逻辑上 tx 的池候选 = 野花 / 全豆要(kg,tx) / 聆澜，三者能力表均含 tx。

## 待判明的三个假设（需可见日志区分）

- **H1 设计内饥饿**：tie-break「同时空闲优先账号」（ADR 0005）。若批次实际并发低
  （任务错峰），账号在途计数为 0 每次都赢平局 → 池颗粒无收。账号 tx 解析带
  CDN 缓存命中（fnameHitCache_200）很快，任务串行化完全可能。
- **H2 熔断隔离**：聆澜在更早的测试中累积了 3+ 次下载失败 → 升级熔断中
  （5→10→…分钟）。到期自动恢复。
- **H3 幸存者归因**：聆澜被选过但其链接下载失败 → refreshUrl 换链 → 账号救活
  → 完成记录只显示最后交付者（同 issues/02 的机制）。

## 已实施：主进程池分发可观测性

`spillUrl` 增加请求级日志（`[pool-main] 解析请求/成功/失败 <成员id> <source/type>`），
池的分发与成败从此在 dev stdout 直接可见——渲染层日志不可达导致的三次盲猜（issues/02、
03、04）就此闭环。下次跑批即可一锤定音。

## 根因（2026-10-15 定案，排除法闭环）

**换源缓存分支短路分发器。** 这批歌曲的 musicInfo 元数据带有此前换源成功后缓存的
`meta.toggleMusicInfo`（用户当天反复下载同一歌单遗留），而 `getUrl` 的换源缓存分支
位于分发器**之前**且无条件命中：缓存匹配直接经 musicSdk（账号优先）解析返回——
73 次 tx 账号解析全部来自该分支；`[dispatch]`/`[pool-main]` 均为 0。
池、tie-break、聆澜从未被询问。换源缓存机制早于音源池存在，属历史遗留短路。

## 修复

换源缓存分支加分发资格门槛：`dispatchEligible = isAccountSourceActive(原平台)`
为真时跳过缓存短路，一律走 账号↔池 分发；缓存匹配对不分发的歌曲
（非账号平台/账号未激活）保留原行为。分支命中现在也打 `[dispatch]` 日志。
